Spire Bench

A shared benchmark for Slay the Spire 2 bots, built so that a reported win rate means the same thing for everyone and cannot be inflated by seed picking, peeking at hidden state, or retrying.

1. Goals

Several people are building StS2 agents and reporting numbers that cannot be compared: different simulators, different seeds, different handling of hidden information. Spire Bench is a proposal for one referee that everyone plays against.

  • Comparable. Same game version, same rules, same observation, same scoring for every bot.
  • Cheat proof for game integrity. No seed farming, no hidden-information leaks, no hindsight or retries, no scouting with a second account.
  • Open to every kind of bot. Neural policies, search bots and LLM agents all play through the same interface.
  • Faithful. The referee runs the real game, and where the headless build differs from the real game, the headless build gets fixed.
  • Checkable. Anyone can verify afterwards that the referee played the recorded games honestly.

Not a goal for the first version: proving how much compute a bot used. Compute is self-declared and shown as a label, with a time limit per decision.

2. What counts as cheating

AttackHow the design stops it
Train on, or pick, favourable seedsThere are no seeds to pick. Randomness comes from a server secret and is fresh for every episode.
Recover the random stream from what you observeThe game's own generator is replaced by a keyed cryptographic one (section 5).
Read hidden state: draw order, enemy AI state, future roomsThe bot receives an allow-listed view. Unknown fields are dropped by default (section 6).
Retry or rewind after a bad outcomeThe game state lives on the server and only moves forward. One action stream per episode.
Quit losing runsAn abandoned or timed-out episode is a loss.
Submit many times and report the bestThe score pools every episode an agent version ever started. All attempts are public.
Scout with a second accountEpisode keys are per agent, so two accounts never see the same dice.
Send actions the game would not offerEvery observation lists its legal actions. Anything else is refused before it reaches the game.
A human plays the hard decisionsVolume under a deadline: thousands of runs with a per-decision time limit.
The host cheatsCommit and reveal of the season secret, public transcripts, and a second operator for the host's own bots (section 9).

3. Design in one picture

The bot never runs the game. It receives what a player would see and answers with one action. The referee holds the secret, runs the real game, and records everything.

One worker process plays one episode. A worker only ever holds the key for its own episode, and has no network access.

Search bots need their own simulator: they rebuild the position from the observation, search locally, and send the chosen action. The referee is far too slow to search in, and it would not let a bot look ahead anyway.

4. The engine

The referee wraps the real game assembly and runs it headless, without the Godot engine. This avoids arguing about whose simulator is right: the rules are whatever the shipped game does.

  • Full runs are supported: all five characters, ascension levels, map, events, shops, rest sites, rewards and act transitions.
  • The game assembly never leaves the host, so nothing of the game is redistributed. Anyone who wants to operate a referee supplies their own copy.
  • Each season pins one game version.

Where the headless build differed from the game

A headless build has no screens, so anything that is a screen in the game needs a deliberate replacement. The rule is that the referee must not depart from the real game. Fixed so far:

  • Crystal Sphere. The headless build used to dig a fixed pattern by itself. In referee mode each divination is now the bot's decision, with both tools available.
  • Trial, "Double Down". In the game this opens the abandon-run confirmation. In referee mode taking it ends the run as a loss.
  • Potion reward on a full belt. Always a decision (discard one or decline), never a silent drop.
  • Act 1 variant. Rolled as the real lobby rolls it.

Other departures may exist. Finding them is one reason to get more bots playing through the referee early.

5. Randomness

Why the game's own generator cannot be used

The game derives every random stream from a 32-bit number hashed from the seed string, and expands it with Xoshiro256**. A bot that sees a few outcomes (the map, an opening hand) can try all 232 seeds, find the matching one, and then predict everything. Keeping the seed secret does not help, and reseeding every floor or every turn does not help either: the draw pile order is fixed at the shuffle, so two observed hands are enough to pin it down.

The keyed generator

Each random stream gets its own key derived from a secret episode key, and the n-th number of a stream is computed directly from that key and n.

stream_key = HMAC-SHA256(episode_key, stream label)
draw[n]    = HMAC-SHA256(stream_key, n)   -> mapped to a range exactly as the game maps it
  • Guessing now means guessing a 256-bit key. Seeing any number of past draws says nothing about the next.
  • The game's seed string becomes a public label and decides nothing.
  • The range mapping is copied from the game, so every distribution is the game's.
  • After every command the referee checks that no draw reached the game's original generator. If one did, the episode is void and the process stops.

Commit and reveal

The same construction lets everyone check the host afterwards.

sequenceDiagram
  participant H as Host
  participant P as Public
  H->>P: Before the season: hash of the secret K, and a future public randomness round
  Note over H: Season key = HMAC(K, that round's value)
Episode key = HMAC(season key, agent, episode number)
  H->>P: During the season: scores only
  H->>P: After the season: K and every transcript
  P->>P: Check the hash, replay any transcript, compare the outcome

Mixing in a public random value that is published after the commitment stops the host from trying many secrets and keeping one that suits its own bot.

6. What a bot sees

An observation holds only what the game screen shows the player. It is built by projecting the engine's internal state onto an allow-list. A field that is on neither the allow-list nor the deny-list is dropped and reported to the operator, so a field nobody thought about cannot leak.

Hidden from the botWhat it gets instead
Draw pile orderThe pile's contents, sorted, without positions. Contents and size are public in the game too.
Seed, stream counters, episode keyNothing.
Enemy AI state and the id of the current moveIntents as shown (type, damage, hits), HP, block, visible powers.
Future rooms, rewards, shop stock, event outcomesEach appears only on the screen that shows it.
The second bossSent once it is the next node on the map. See question Q3.
What lies under fogged Crystal Sphere cellsFor cleared cells only: the piece of the item drawn there.

Decision types: map_select (with the whole act map), combat_play, card_reward, card_select, bundle_select, event_choice, rest_site, shop, potion_swap, crystal_sphere, game_over.

A bot that remembers what it has seen, for example a card it put on top of its draw pile, keeps that knowledge itself. The referee does not track it.

7. Actions and errors

Every observation carries legal_actions: the complete list of actions the bot may send, in exactly the shape it sends them. The referee refuses anything not on the list before it touches the game.

{
  "type": "decision",
  "decision": "combat_play",
  "energy": 3,
  "hand": [{"index": 0, "id": "CARD.BASH", "cost": 2, "can_play": true, "target_type": "AnyEnemy"}, ...],
  "enemies": [{"index": 0, "name": "Seapunk", "hp": 46, "intents": [{"type": "Attack", "damage": 11, "hits": 1}]}],
  "draw_pile": [...sorted, no positions...],
  "legal_actions": [
    {"action": "play_card", "args": {"card_index": 0, "target_index": 0}},
    {"action": "end_turn"}
  ]
}

bot sends:  {"action": "play_card", "args": {"card_index": 0, "target_index": 0}}

Picking several cards is listed as one entry with a rule (choose between min and max of these indices) instead of every combination.

Error codeMeaning
illegal_actionNot in legal_actions. The decision stands; send another.
bad_requestMalformed message.
not_availableA command the referee does not offer.
rejectedThe game refused a listed action. This is a referee bug and should be reported.
internalThe referee failed.

Errors carry a code and no text, because free text from the engine can quote internal state.

8. Episodes and scoring

  • An episode is one full run for one character at one ascension level, on fresh randomness.
  • Episode numbers are assigned by the server in order. A bot cannot ask for a different one.
  • Each decision has a time limit, and so does the whole run. Timeouts, disconnects past a short resume window, and abandoned runs are losses.
  • The score of an agent version is its win rate over every episode it ever started, with a confidence interval, per character and ascension.
  • Dice are independent per agent. This rules out scouting, at the price of paired comparisons between agents.

9. Trusting the host

Whoever hosts can see the season secret while games are running. Commit and reveal proves the host did not change or choose the dice, but it cannot prove the host did not feed foresight to its own bot. So:

  • The referee software is open, and anyone with a copy of the game can run one.
  • A host's own bots are scored on a referee run by someone else. The board shows which referee produced each score.
  • All transcripts are published after the season, so any game can be replayed by anyone.

10. What exists today

The worker side is built and tested on game version 0.107.1. The gateway, accounts, scoring and the client library are not built yet.

The first four rows are the headless game without the referee layer, playing combats only, from an earlier careful benchmark. A game process spends most of its wall time asleep, so several can share a core. The referee rows come from short test runs on a machine that was busy with other work; the CPU cost the referee adds per action has not been measured separately.

If a full run is about 1,500 actions, which has not been measured, one 24-core machine plays on the order of eight runs per second before start-up cost, so 1,000 runs take minutes, not hours. That is fine for evaluation. It is still about 1,500 times slower per core than a purpose-built simulator, which is why search bots bring their own.

11. Open for discussion

Numbered so they can be referred to in chat. "Current position" is what the draft does today, not a decision for the group.

  1. Q1

    What is the headline number?

    open

    Proposal: full-run win rate per character at ascension 10, plus an all-ascension average. Should there also be a cheaper combat-only track on fixed positions?

  2. Q2

    Which game version, and how often does it move?

    open

    The game is in early access and changes quickly. Proposal: one pinned version per season, scores never compared across seasons. The referee currently runs 0.107.1 only.

  3. Q3

    When does a player see the second boss?

    needs an in-game check

    Current position: hidden until it is the next node. A reading of the 0.107.1 map screen code suggests the second boss node is drawn with its own art from the start of the act. Someone should check in the game at ascension 10, and the referee should then match it.

  4. Q4

    Enemy move ids stay hidden

    current position

    Bots get intents, not move ids, like a player. A bot's simulator has to infer the move from the intent and the history. Does that break anyone's state reconstruction?

  5. Q5

    Is the observation enough to rebuild the position?

    open

    Search bots must load the observation into their own simulator. Which fields are missing or awkward for yours? Canonical ids, power internals, relic counters?

  6. Q6

    Compute classes and time limits

    open

    Current position: one open board, compute self-declared as a label (no search, search, LLM), and a per-decision time limit. What limit works for LLM agents without letting a human sit in the loop?

  7. Q7

    Minimum runs for a listed score

    open

    1,000 runs give about ± 2.7 points. LLM agents may only afford 100. Show everything with its interval, or require a floor?

  8. Q8

    Independent dice per agent

    current position

    Shared dice would allow paired comparisons with far fewer runs, but a second account could scout them. Is losing paired comparison acceptable?

  9. Q9

    Public transcripts

    open

    Verification needs every game published after the season. That also shows how each bot plays. Is everyone comfortable with that?

  10. Q10

    Who hosts, and who is the second operator?

    open

    The host needs a copy of the game and a machine with spare cores. A second person has to run a referee for the host's own entries.

  11. Q11

    Identity and submission limits

    open

    One account per person, tied to a chat identity? A cap on runs per day to keep hosting cost bounded?

  12. Q12

    Potions outside combat

    not built

    The legal action list offers potions during combat only. Using or discarding one on other screens is not listed yet.

  13. Q13

    Other places the headless build differs from the game

    open

    Two were known and are fixed. If you know of a screen, event or prompt that a headless build handles differently from the game, name it.

  14. Q14

    Effects that hide intents

    checked by reading only

    No player-side effect that hides intents was found in 0.107.1; moves with a hidden intent are sent as intent type Hidden. Not verified in play.
