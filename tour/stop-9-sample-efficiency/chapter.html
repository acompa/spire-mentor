RL Tour 9: Sample efficiency

Sample efficiency is how much a training run learns for what it spends. The phrase covers three different quantities, and a change that improves one can worsen another. This chapter separates them, works out when reusing data or growing the batch pays off, and uses them to read Spire Mentor's learning curve over nine billion decisions.

1. Three numbers share one name

In November 2026 Spire Mentor's Ironclad network trained for nine billion decisions and finished at 81.4% on its development seeds. Early in that run the author switched the update from two passes over each batch to one. Afterwards the learner played 43% more decisions per second, and each decision fed half as many gradient steps. Did the run become more sample-efficient or less?

Both answers are defensible, because "sample efficiency" names at least three different quantities:

  1. Learning per decision. The number of environment decisions the run needs to reach a given level. Most papers mean this one, and reusing data improves it.
  2. Learning per second. The wall-clock time the run needs to reach that level. It equals the first quantity divided by the decisions played per second, so a change that makes decisions cheaper can win here while losing on the first.
  3. Seeds per conclusion. The number of independent runs you need before you can say one recipe beats another. Chapter 8 covers this for fixed networks, and Section 8 below adds what changes when you compare training runs instead.

The epoch switch probably cost the first quantity and gained the second. Whether it gained more than it cost depends on a ratio that the campaign never measured. This chapter derives that ratio, shows why on-policy methods spend decisions as they do, explains why doubling the batch helped twice and then stopped, and ends with how many seeds a comparison of two training runs needs.

2. A milestone turns a curve into a number

A learning curve plots the policy's score against what training has spent. Here the spend is decisions, \(D\), and the score \(S(D)\) is whatever you evaluate the policy on. In Spire Mentor it is the win rate on a fixed panel of development seeds.

Take one run whose score crosses 60% after 440 thousand decisions. Draw a horizontal line at 60% and drop a vertical line where the curve first meets it. The decisions at that point are the run's decisions to milestone.

Definition 9.1 · Decisions to milestone

For a milestone score \(S^\star\), the decisions to milestone are

\begin{equation} D^\star(S^\star) = \min\{\, D : S(D) \ge S^\star \,\}. \label{eq:dstar} \end{equation}

A smaller \(D^\star\) means the run learned more per decision, up to that level. Equation \eqref{eq:dstar} says nothing about the run after the milestone. A run can reach 60% quickly and stall at 75%.

Now add a second run. Run B climbs faster at first and levels off lower. It reaches 60% at 190 thousand decisions, less than half of run A's \(D^\star\), but it never reaches 80%.

So the milestone you pick decides which run looks more efficient. A common alternative avoids picking one by averaging the score over the whole budget \(D_{\max}\):

\begin{equation} \mathrm{AUC} = \frac{1}{D_{\max}} \int_0^{D_{\max}} S(D)\, dD. \label{eq:auc} \end{equation}

The area under the curve, AUC, rewards early learning and late level together. It also hides the trade between them, and it depends on \(D_{\max}\). Stretch the budget and run A's high plateau dominates. Shorten it and run B's fast start does. When you report an AUC, report the budget with it.

3. Wall clock divides by throughput

Decisions are not free, and different recipes pay different prices for them. If a run plays \(R\) decisions per second, the wall-clock time to a milestone is

\begin{equation} w^\star = \frac{D^\star}{R}. \label{eq:wall} \end{equation}

Suppose run A in Figure 9.1b is cheap to run and plays three decisions in the time run B plays one. Redraw both curves against seconds instead of decisions. Run A's curve compresses horizontally by a factor of three, and it now reaches 60% first.

Equation \eqref{eq:wall} is why "more sample-efficient" and "faster" are different claims. Methods that reuse data, such as replay buffers or extra update epochs, lower \(D^\star\) and usually lower \(R\) too, because each decision now costs more computation. A fast, cheap simulator such as Spire Mentor's favours spending more decisions and less computation on each one.

The third quantity, seeds per conclusion, matters because every \(D^\star\) and every AUC is measured on one training run, and a second run with a different random seed gives a different number. Chapter 8 shows how to size an evaluation of one fixed network. Section 8 below extends that to training runs.

4. On-policy learning uses each decision a few times

DQN's answer to sample efficiency is a replay buffer. Every transition goes into the buffer, and the learner samples minibatches from it for a long time afterwards. Fedus et al. define the replay ratio as gradient updates per environment transition [3]. DQN's settings make one update every four environment steps, a ratio of 0.25, with a buffer of one million transitions. With a minibatch of \(N\) transitions per update, each transition is sampled on average

\begin{equation} \text{uses per transition} = N \times \text{replay ratio} = 32 \times 0.25 = 8 \label{eq:reuse} \end{equation}

times over its life in the buffer. The 32 is DQN's minibatch size, and the arithmetic is mine, not the paper's. With a one-million buffer, Fedus et al. note, the oldest data in it came from a policy 250 thousand updates old.

The reuse is valid because of the form of Q-learning's target. The target \(r + \gamma \max_{a'} Q(s', a')\) is a fact about the environment and the current Q-function. It does not mention the policy that chose \(a\), so any transition from any earlier policy is a fair training example.

The policy gradient is different. From chapter 5, the gradient of the objective is an expectation over the states the current policy visits and the actions it takes there:

\begin{equation} \nabla_\theta J(\theta) \propto \mathbb{E}_{s \sim d^{\pi},\, a \sim \pi_\theta(\cdot \mid s)}\!\left[\nabla_\theta \log \pi_\theta(a \mid s)\, A^{\pi}(s, a)\right]. \label{eq:onpolicy} \end{equation}

Data collected by an older policy \(\mu\) estimates a different expectation. Chapter 6 corrected the action part of this with the importance ratio, which reweights each old action at a given state:

\begin{equation} \mathbb{E}_{a \sim \pi_\theta(\cdot \mid s)}\!\left[\nabla_\theta \log \pi_\theta(a \mid s)\, A^{\pi}(s, a)\right] = \mathbb{E}_{a \sim \mu(\cdot \mid s)}\!\left[\rho\, \nabla_\theta \log \pi_\theta(a \mid s)\, A^{\pi}(s, a)\right], \qquad \rho = \frac{\pi_\theta(a \mid s)}{\mu(a \mid s)}. \label{eq:offpolicy} \end{equation}

Equation \eqref{eq:offpolicy} holds at each state. The states themselves still come from \(\mu\)'s visits, which the ratio does not correct, so the reweighted gradient is close to unbiased only while the two policies stay close (chapter 6). Its variance also grows with how far \(\pi_\theta\) has moved from \(\mu\), and the second moment of the ratio puts a lower bound on that growth:

\begin{equation} \mathbb{E}_{\mu}\!\left[\rho^2\right] = \sum_a \frac{\pi_\theta(a)^2}{\mu(a)} = \mathbb{E}_{\pi_\theta}\!\left[\rho\right] \ \ge\ \exp\!\big(\mathbb{E}_{\pi_\theta}[\log \rho]\big) = \exp\!\big(D_{\mathrm{KL}}(\pi_\theta \,\|\, \mu)\big). \label{eq:secondmoment} \end{equation}

We wrote the sum as an expectation under \(\pi_\theta\), then applied Jensen's inequality to the convex function \(\exp\). The result says the ratio's second moment, and so the variance it adds to each term, grows at least exponentially in the KL divergence between the two policies. A buffer that holds data from 250 thousand updates ago would be unusable for a policy gradient. Chapter 6 measured the same effect as a loss of effective sample size.

PPO's compromise is to collect a batch of \(B\) decisions with the current policy, take \(E\) passes over it in minibatches while the clip keeps \(\rho\) near 1, and then throw the batch away. Each decision feeds up to \(E\) gradient steps. The PPO paper's Algorithm 1 has this shape, and its defaults used 10 epochs for MuJoCo and 3 for Atari [6].

This is why chapter 5 rejected the idea that a replay buffer would make PPO more sample-efficient. Replay can raise learning per decision for Q-learning because Q-learning's target ignores the behaviour policy. For a policy gradient the old data has to be reweighted, and Equation \eqref{eq:secondmoment} sets the price. On-policy methods give up learning per decision, and in exchange each update starts from data the current policy collected, with no ratio to correct.

5. A second epoch must beat its cost in time

Within PPO, the epoch count \(E\) is the one lever that reuses data. Raising \(E\) from one to two puts each decision into two gradient steps instead of one. If the second pass over the batch were as useful as the first, the run would need half the decisions to reach any milestone. It is not as useful, for two reasons. The policy has already moved on the first pass, so the clip zeroes the gradient on more rows. And the second pass fits the same \(B\) samples again, including their noise.

Let \(\Delta J(E)\) be the improvement in the objective from one update with \(E\) epochs, and let \(t(E)\) be the wall-clock seconds one update takes, collection included. With \(B\) decisions per update, the progress per decision and per second are

\begin{equation} \frac{\Delta J(E)}{B} \quad \text{per decision}, \qquad \frac{\Delta J(E)}{t(E)} \quad \text{per second}. \label{eq:rates} \end{equation}

Write the gain of the second epoch as a fraction \(q\) of the first, so that \(\Delta J(2) = (1 + q)\,\Delta J(1)\) with \(0 \le q \le 1\). Per decision, two epochs always win when \(q > 0\). Per second, two epochs win only if

\begin{equation} \frac{\Delta J(2)}{t(2)} > \frac{\Delta J(1)}{t(1)} \iff 1 + q > \frac{t(2)}{t(1)}. \label{eq:breakeven} \end{equation}

The right-hand side depends on the machine and the software, and the left-hand side on the learning problem at that point in training. Both can be measured, and neither is known in advance.

If \(\Delta J\) per update stays roughly constant along the way to a milestone, the number of updates to reach it scales as \(1/\Delta J\). The decisions to the milestone then satisfy \(D^\star(1)/D^\star(2) \approx 1 + q\), and the condition becomes a statement about two measurable learning curves:

\begin{equation} w^\star(2) \lt w^\star(1) \iff \frac{D^\star(1)}{D^\star(2)} > \frac{t(2)}{t(1)}. \label{eq:breakevenD} \end{equation}

Equation \eqref{eq:breakevenD} needs no assumption about \(\Delta J\). It follows from \(w^\star = I^\star\, t\), where \(I^\star = D^\star / B\) is the number of updates to the milestone.

In Spire Mentor

The campaign started with \(E = 2\) and 131,072 decisions per update. Its log timed one iteration at 20.3 seconds: 12.9 s of collection, 1.0 s to cut the batch, and about 4 s of waiting while the update finished. The update itself was a 3-second pre-pass and 12 seconds of gradient steps, running on other GPUs while the next batch was collected (CAMPAIGN_LOG.md, line 143).

After the switch to \(E = 1\) at about 551 million decisions, the update took 4.8 to 6.7 s plus the pre-pass, and the rate rose to about 9,100 decisions per second, "+43%" (line 145). At that rate an iteration takes \(131{,}072 / 9{,}100 = 14.4\) s, so \(t(2)/t(1) = 20.3/14.4 = 1.41\). By Equation \eqref{eq:breakeven}, the second epoch was worth its time only if it added more than 41% of the first epoch's progress, that is, \(q > 0.41\).

Nobody measured \(q\) for this network. The plan's revert rule compared the network at 885 million decisions with the pinned network from before the switch, 41.3% against 30.9% (line 152). That shows the run kept learning after the switch. It does not show what \(E = 2\) would have done over the same 335 million decisions, because no \(E = 2\) arm ran alongside. The KL term toward the teachers also reached zero at 500 million decisions (chapter 7), 51 million decisions before the switch, so the two changes are confounded in any before-and-after reading.

Section 12 runs the comparison on a toy problem where \(q\) can be measured, and shows that it depends on the learning rate.

6. Gradient noise sets what a batch can buy

The other way to change sample efficiency without changing the algorithm is to change how many decisions go into each update. Supervised learning has a well-tested model of this, from McCandlish et al. [1]. Their paper writes the learning rate as \(\epsilon\), steps as \(S\) and examples as \(E\). Those letters already mean the clip range, a state and epochs in this tour, so below the learning rate is \(\alpha\), the number of updates is \(I\), the examples are decisions \(D\), and the true gradient is \(g\) instead of their \(G\).

Start with a loss \(L(\theta)\), its gradient \(g\) and its Hessian \(\mathbf{H}\). A batch of \(B\) independent samples gives an estimate \(\hat g\) with mean \(g\) and covariance \(\Sigma / B\), where \(\Sigma\) is the covariance of one sample's gradient. Take one step of size \(\alpha\) and expand the loss to second order:

\begin{equation} \mathbb{E}\big[L(\theta - \alpha \hat g)\big] \approx L(\theta) - \alpha\, |g|^2 + \tfrac{1}{2}\alpha^2 \left( g^{\top}\mathbf{H}\,g + \frac{\mathrm{tr}(\mathbf{H}\Sigma)}{B} \right). \label{eq:taylor} \end{equation}

The noise enters only through the last term, through \(\mathbb{E}[\hat g^{\top}\mathbf{H}\hat g] = g^{\top}\mathbf{H}g + \mathrm{tr}(\mathbf{H}\Sigma)/B\). We minimise the right-hand side over \(\alpha\), which is a quadratic in \(\alpha\):

\begin{equation} \alpha_{\text{opt}}(B) = \frac{\alpha_{\max}}{1 + B_{\text{noise}}/B}, \qquad \alpha_{\max} = \frac{|g|^2}{g^{\top}\mathbf{H}g}, \label{eq:alphaopt} \end{equation}
\begin{equation} \Delta L_{\text{opt}}(B) = \frac{\Delta L_{\max}}{1 + B_{\text{noise}}/B}, \qquad \Delta L_{\max} = \frac{|g|^4}{2\, g^{\top}\mathbf{H}g}, \label{eq:dlopt} \end{equation}

where the noise scale is

\begin{equation} B_{\text{noise}} = \frac{\mathrm{tr}(\mathbf{H}\Sigma)}{g^{\top}\mathbf{H}g} \ \approx\ B_{\text{simple}} = \frac{\mathrm{tr}(\Sigma)}{|g|^2}. \label{eq:bnoise} \end{equation}

These are the paper's Equations 2.5 to 2.9, renamed. \(B_{\text{simple}}\) drops the Hessian, which is hard to measure; it equals \(B_{\text{noise}}\) when \(\mathbf{H}\) is a multiple of the identity.

Read Equation \eqref{eq:dlopt} at two extremes. When \(B \ll B_{\text{noise}}\), the improvement per step is about \(\Delta L_{\max} B / B_{\text{noise}}\), proportional to \(B\). Doubling the batch then doubles the progress per step, so the progress per decision does not change, and you finish in half the steps. This holds with the learning rate re-tuned to \(\alpha_{\text{opt}}(B)\), which in this regime grows about in proportion to \(B\). At a fixed \(\alpha\), Equation \eqref{eq:taylor} gives a per-step gain that does not double with \(B\). When \(B \gg B_{\text{noise}}\), each step already gets nearly \(\Delta L_{\max}\), and doubling the batch doubles the decisions for almost nothing.

If every step makes progress \(\Delta L_{\text{opt}}(B)\), reaching a fixed loss takes \(I = I_{\min}(1 + B_{\text{noise}}/B)\) steps and \(D = IB = I_{\min}(B + B_{\text{noise}})\) decisions. Write \(D_{\min} = I_{\min} B_{\text{noise}}\) for the small-batch limit. Then \(I/I_{\min} - 1 = B_{\text{noise}}/B\) and \(D/D_{\min} - 1 = B/B_{\text{noise}}\), and the two multiply to one:

\begin{equation} \left(\frac{I}{I_{\min}} - 1\right)\left(\frac{D}{D_{\min}} - 1\right) = 1, \qquad B_{\text{crit}} = \frac{D_{\min}}{I_{\min}} \approx B_{\text{noise}}. \label{eq:tradeoff} \end{equation}

These are the paper's Equations 2.11 and 2.12. The critical batch size \(B_{\text{crit}}\) is where you pay twice the minimum in both updates and decisions. Below it, a bigger batch buys fewer updates at almost no cost in decisions. Above it, a bigger batch costs decisions and saves few updates. McCandlish et al. also report that the noise scale grows during training, because \(|g|\) shrinks as the loss falls while \(\Sigma\) does not. They measured it on Atari and Dota 2 as well as on supervised tasks.

A constant step leaves a noise floor

Equation \eqref{eq:taylor} describes one step. Over many steps at a fixed \(\alpha\), the noise also stops the loss from reaching its minimum. McCandlish et al.'s Appendix C models SGD near a minimum as a process whose parameter covariance \(M\) settles where

\begin{equation} \mathbf{H}M + M\mathbf{H} = \frac{\alpha}{B}\,\Sigma \quad\Longrightarrow\quad \mathbb{E}[L] - L^{\min} = \tfrac{1}{2}\,\mathrm{tr}(\mathbf{H}M) = \frac{\alpha\, \mathrm{tr}(\Sigma)}{4B}. \label{eq:floor} \end{equation}

The step from their equation to the floor is ours. We took the trace of both sides and used \(\mathrm{tr}(\mathbf{H}M) = \mathrm{tr}(M\mathbf{H})\), which gives \(2\,\mathrm{tr}(\mathbf{H}M) = (\alpha/B)\,\mathrm{tr}(\Sigma)\). The loss near the minimum is \(\tfrac12 (\theta - \theta^{\min})^{\top}\mathbf{H}(\theta - \theta^{\min})\), whose expectation is \(\tfrac12 \mathrm{tr}(\mathbf{H}M)\).

Equation \eqref{eq:floor} depends on \(\alpha\) and \(B\) only through \(\alpha/B\). Halving the learning rate and doubling the batch both halve the floor. Each halving buys half as much as the one before, and once the floor sits below some other error, such as the network's capacity, further halvings buy nothing visible. Equation \eqref{eq:floor} is a small-step limit. For a quadratic with curvatures \(h_i\) and diagonal \(\Sigma\), the exact floor of discrete steps is \(\frac{\alpha}{2B}\sum_i \frac{\Sigma_{ii}}{2-\alpha h_i}\), which approaches Equation \eqref{eq:floor} when every \(\alpha h_i\) is small. Section 12 checks both on a noisy quadratic.

PPO's outer loop

A PPO update is not one SGD step. It is \(E\, B / N\) minibatch steps on a surrogate built from one batch. Beukman et al. treat the sequence of updates, the outer loop, as a stochastic optimiser of its own [2]. In that view the outer step size is how far one update moves the policy, and the outer noise comes from estimating the surrogate on \(B\) samples. A plateau appears when the step is too large for the noise, and the policy wanders around a local optimum instead of settling into it. They prescribe more samples per update while keeping the minibatch size and learning rate fixed, which adds minibatch steps. Their diagnostic is the data-to-divergence ratio:

\begin{equation} \mathrm{DDR} = \frac{B}{D_{\mathrm{KL}}(\pi_{\theta_{k+1}} \,\|\, \pi_{\theta_k})}, \label{eq:ddr} \end{equation}

the data in one update divided by how far that update moved the policy away from the one that collected it. A run with low DDR plateaus early, and one with high DDR learns slowly for a fixed budget. They argue DDR should rise as the training budget grows. Section 11 computes it for Spire Mentor's three doublings.

7. Each lever trades decisions for something else

Epochs and batch size are two levers on \(D^\star\). Four more follow, and each has a cost.

A teacher or a warm start. Start from a network that already plays, or add a loss that pulls the student toward a teacher. Chapter 7 covers both. The early part of the learning curve shifts left, sometimes by a lot. The cost is the teacher's data and computation, and the student can inherit the teacher's mistakes. Spire Mentor's campaign used both, with a teacher KL term whose weight fell to zero at 500 million decisions. Its random-weight learning checks, in Section 11, show the network can learn without a teacher, at least at the start.

Restarts and curricula. Begin some episodes from states where the policy tends to fail, or order the tasks from easy to hard. Decisions then land where the gradient carries signal instead of on parts of the game the policy has already learned. The training distribution then differs from evaluation, so the policy can overfit the restart states. Spire Mentor's plan devotes a share of slots to practice fights started from saved states: 40% of slots falling to 25% over the first two billion decisions, with a growing share on bosses (docs/plans/2026-11-02-ironclad-e2e-ppo-v0111.md, line 198).

Reuse of stale data. Train on decisions collected by a policy a few updates old. This raises learning per decision the way replay does for DQN. The price is the variance of Equation \eqref{eq:secondmoment}, or the bias of a clamped ratio. Chapter 6 shows how Spire Mentor holds back run-level rows for about four iterations, sometimes longer, and corrects them.

Search at play time. Spend computation at each decision instead of during training. A tree search over a weaker network can play as well as a stronger network without search. Jones found, for AlphaZero on the board game Hex, that each extra factor of ten in training computation could replace about fifteen times as much test-time computation at the same strength [8]. You pay that computation in every game you play. This lever leaves the learning curve unchanged and lowers the level the curve has to reach.

8. Comparing two runs needs several seeds each

A learning curve is one random draw. Change the training seed and the curve changes: different decisions get sampled, different minibatches get drawn, and the network starts from different weights. Henderson et al. ran ten TRPO trials on HalfCheetah with identical settings, split them into two groups of five, and got two average curves that a t-test called different, \(t = -9.09\), \(p = 0.0016\) [4]. Colas et al. repeated the exercise with DDPG, five seeds per "algorithm", and a Welch t-test found a difference at \(p = 0.031\) between two copies of the same code [5].

The comparison you want is between two expected values. Let arm A and arm B each run \(n\) training seeds, let \(\sigma_\star\) be the standard deviation of \(D^\star\) across seeds, and let \(\Delta^\star = \mathbb{E}[D^\star_A] - \mathbb{E}[D^\star_B] > 0\), so B is truly better. If you pick the arm with the smaller mean \(D^\star\), the difference of the two means has standard deviation \(\sigma_\star\sqrt{2/n}\). Under a normal approximation you pick the wrong arm with probability

\begin{equation} P(\text{wrong pick}) \approx \Phi\!\left(-\frac{\Delta^\star}{\sigma_\star}\sqrt{\frac{n}{2}}\right), \label{eq:wrongpick} \end{equation}

where \(\Phi\) is the standard normal CDF. The ratio \(\Delta^\star/\sigma_\star\) is the effect measured in seeds' worth of spread. When it is 1, one seed per arm picks wrong about 24% of the time, three seeds about 11%, \(\Phi(-\sqrt{1.5})\), and it takes six seeds to bring the rate down to about 4%. Colas et al. turn the same arithmetic into a power analysis and recommend a pilot of at least 20 seeds to estimate the spread [5]. Agarwal et al. found that published deep-RL results often used three to ten runs, and recommend reporting interval estimates and robust aggregates such as the interquartile mean [7].

Early learning does not reliably predict late learning

A training run is expensive, so it is tempting to stop both arms early and keep the one ahead. Figure 9.1b already shows how that can fail: run B leads at every point before the curves cross. Across seeds of one recipe, the same problem appears in a weaker form. A seed that learns quickly at first need not reach the high milestone first. In the bandit toy of Section 12, the rank correlation between decisions to 50% and decisions to 90% across 200 seeds was only 0.23 and 0.38 for the two arms. That is a toy result, not a measurement of Spire Mentor. If you compare arms early, say so, and pre-register the early milestone as the endpoint instead of presenting it as a proxy for the late one.

Several arms multiply the false alarms

With \(K\) arms that are all equal to the control, each tested at level \(\alpha_{\text{test}}\), the chance that at least one test fires is

\begin{equation} P(\text{at least one false positive}) \le 1 - (1 - \alpha_{\text{test}})^{K}, \label{eq:familywise} \end{equation}

with equality when the \(K\) tests are independent. Tests that share one control arm are positively correlated, and for them the bound holds. At \(\alpha_{\text{test}} = 0.05\) the bound is 9.8% for two arms, 18.5% for four and 33.7% for eight. Chapter 8 wrote the test level as \(\alpha\); here \(\alpha\) is the learning rate, so the level gets a subscript. The Bonferroni correction tests each arm at \(\alpha_{\text{test}}/K\), which keeps the probability in Equation \eqref{eq:familywise} below \(\alpha_{\text{test}}\); Colas et al. recommend it for exactly this case [5]. Chapter 8 showed the related problem of picking the best of \(K\) checkpoints on the same seeds that rank them.

9. State the hypothesis as decisions to a milestone

A sample-efficiency claim is clearest when it names one quantity, one milestone and one budget before any run starts. It fixes five things:

  1. The change and the control, identical in everything else, including decisions per update and, for a short run, the number of updates.
  2. The score \(S\), the panel of seeds it is read on, and how often it is read.
  3. The milestone \(S^\star\) and the budget. A run that never reaches \(S^\star\) within the budget is recorded as "more than the budget", not dropped.
  4. The number of training seeds per arm, from a pilot estimate of \(\sigma_\star\) and Equation \eqref{eq:wrongpick}.
  5. Whether the claim is per decision, per second, or both. A per-second claim also records \(R\) for each arm on the same machine.

10. A real campaign is not one curve

A textbook comparison of sample efficiency trains several fixed configurations, several seeds each, and plots score against environment steps. The Atari 100k benchmark is the standard example: every agent gets the same 100 thousand steps, and Agarwal et al. analyse its results with up to 100 runs per game [7].

Spire Mentor's campaign is a single run that was changed along the way. Between launch and nine billion decisions the record shows a teacher phase, an epoch switch, an engine update, a halved learning rate, three doublings of the batch and an annealed learning rate. The teacher phase was part of the plan from the start. Each later change was a recorded amendment to the pre-registered plan, and the pre-registration states a reason for each. The switch to one epoch (Amendment 5) came when the run was playing about 6,400 decisions per second, too slow for the schedule, with the learner blocked on the update for about 20% of each iteration. The engine update (Amendment 6) moved training to an engine build with fixes. The learning rate was halved (Amendment 8) after a higher rate had "bought no speed and cost ~3pp of level". Only the three doublings (Amendments 14 to 16) and the anneal (Amendment 17) followed development reads that had stopped climbing.

So the curve records a sequence of recipes, not the learning curve of any one configuration. Its \(D^\star\) for a milestone is what that sequence needed, warm start included. The record gives no bound, in either direction, on what the final recipe would need from random weights. It is also one seed.

The campaign also does things the textbook comparison does not. It reads the development panel at fixed decision counts, with the same seeds every time, and compares reads with paired tests. It counts decisions, not episodes or frames, because runs vary in length. And it counts wall clock as a cost in its own right, since the plan budgets days, not steps.

11. In Spire Mentor

Figure 9.3 is the campaign's learning curve on a log scale of decisions, with every change marked. Until 4 billion decisions the regular reads used weights averaged with a decay of 0.996, then the campaign switched to a slower average, 0.999. Both series are plotted where they exist.

Measured · from the author's campaign log

Reading Figure 9.3 against milestones gives \(D^\star\) values for this one lineage. The averaged network first read at or above 40% at 750 million decisions (43.6%, line 148), at or above 60% at 3.0 billion (61.6% with the slower average, line 187), at or above 70% at 4.75 billion (70.8%, line 231), and at or above 80% at 8.5 billion (81.3%, line 294). The final network read 81.4% on 2,000 development seeds at 9.0 billion (line 300) and 81.38% on 4,000 sealed test seeds (line 308).

Each of those numbers is one read of one run. Neighbouring reads moved by several points with no amendment between them: 38.6% at 595 million and 43.6% at 750 million (lines 146 and 148), and 59.0% at 3.5 billion and 63.6% at 3.75 billion (lines 197 and 201). During the anneal, when the recipe was changing slowly, the reads went 79.3%, 76.8% and 81.3% at 8.0, 8.25 and 8.5 billion (lines 288, 290 and 294), a move of 4.5 points between the last two.

The epoch switch

Section 5 gives the numbers, and Figure 9.4 draws the two iteration times.

The update runs on other GPUs while the workers collect the next batch. With two epochs the update took longer than the collection and the learner waited, while with one epoch it fits inside the collection. That is why removing an epoch made each decision cheaper. At two epochs the learner waited about 4 seconds per iteration for the update (line 143); the log does not break down the rest of the 5.9-second difference between the two iteration times. On a machine where the update already fits inside collection, a second epoch costs almost nothing per second, \(t(2)/t(1)\) is close to 1, and Equation \eqref{eq:breakeven} favours two epochs for any \(q > 0\).

The loop takes about \(E \cdot B / N\) optimiser steps per update. With \(N = 8{,}192\) and \(B = 131{,}072\) that is about 16 steps per epoch. The code counts the rows it actually trains on, not \(B\), and the KL stop can end an update before all \(E\) epochs run. The KL measured at the end of each epoch is the probe_kl the campaign log reports.

The three doublings

After the learning rate was halved at 4.08 billion decisions, the training win rate rose by about 6.5 to 7 points within 200 million decisions (line 217), and the gap between the raw and the averaged weights shrank from 12.75 points at 4.0 billion to 4.80 at 5.0 billion (lines 212 and 254). Read through Equation \eqref{eq:floor}, a smaller step lowered the noise floor; that reading is mine, not the record's. The campaign then doubled the decisions per update three times, each time after the development reads had stopped climbing. Amendment 14 gives the reasoning: "lower update noise bought level, and doubling the samples per update lowers it further".

Each doubling kept the minibatch at 8,192 rows, one epoch and the same learning rate. So the noise in each optimiser step stayed the same, and each update took twice as many optimiser steps on a batch twice as large. That is Beukman et al.'s remedy for the outer loop, not a larger minibatch, and the pre-registration cites their paper for it.

Measured · from the author's campaign log

Twice the decisions per update moved the policy only a little further. The median probe_kl rose by a factor of 1.43, 1.23 and 1.07 across the three doublings, so DDR rose by factors of 1.39, 1.63 and 1.87. The throughput rose slightly each time, from 9,297 to 9,818, from 9,257 to 10,318, and from 10,251 to 10,479 decisions per second, so the doublings cost no wall-clock time per decision.

The first two doublings were each followed by a level step of about 3.5 to 4 points within about 400 million decisions. The third was followed by none that the reads could detect: +1.1 points, p 0.51. The anneal of the learning rate to zero then added about 3 points with averaged weights and 8 with raw weights (docs/site/training.html, lines 327 to 336).

The record does not explain why the third doubling bought nothing, and no experiment isolated it. Two explanations fit the numbers; both are my inference. First, the third doubling raised DDR the most, using a "before" KL borrowed from 1.2 billion decisions earlier, so if the outer-loop noise had still been the limit, it should have helped the most. That it did not suggests the remaining gap was no longer set by update noise. The anneal, which shrinks the step instead, still helped. Second, by analogy with Equation \eqref{eq:floor} applied to the outer loop, each halving of the update noise should buy less than the last. That alone does not explain a drop from 3.9 points to 1.1. Equation \eqref{eq:floor} itself predicts no change from the doublings, because the minibatch and the learning rate stayed fixed.

The project's training page also says that "a measurement of the gradient noise had put the useful batch size near 1.7 million decisions" (docs/site/training.html, lines 329 and 330). The campaign log and the plan do not record how that number was measured, so this chapter treats it as unverified. If it holds, the third doubling, to 1.05 million, was still below it, and the noise model alone does not explain why that doubling bought nothing.

12. Measured on three toy problems

The campaign ran each recipe once, so its numbers cannot separate a mechanism from the luck of one seed. The three problems below are small enough to run many times in seconds. They test the equations of this chapter, not Spire Mentor. figures.py runs all three.

The noise floor on a quadratic

The loss is \(\tfrac12 \sum_i h_i \theta_i^2\) in 50 dimensions, with curvatures \(h_i\) spaced from 0.05 to 1. Each step sees the true gradient plus normal noise of covariance \(I/B\), so \(\mathrm{tr}(\Sigma) = 50\). Four hundred copies run in parallel, and the floor is the average loss over the last 500 of 1,500 steps.

Measured · a toy problem, not Spire Mentor and not a language model

In all 20 settings the measured floor was within 4.7% of the exact discrete-step value \(\frac{\alpha}{2B}\sum_i \frac{\Sigma_{ii}}{2-\alpha h_i}\), and within 1.3% in 18 of them. The small-step limit \(\alpha\,\mathrm{tr}(\Sigma)/4B\) of Equation \eqref{eq:floor} is below every measurement: the measured floors exceed it by up to 5.5% for \(\alpha \le 0.2\), and by 7.1% to 7.3% at \(\alpha = 0.4\), where \(\alpha h_i\) is no longer small. In the schedule of Figure 9.7, the floor went 5.35, 2.59, 1.29, 0.64: each change halved it, so each bought half the absolute improvement of the one before. Doubling the batch did exactly what halving the learning rate did, and spent twice the decisions per step to do it.

Epochs on a contextual bandit

The policy is a softmax over 8 actions in each of 20 contexts. Each action pays 1 with a fixed probability drawn once at random. Each update collects 512 decisions, normalises the advantages, and takes \(E\) passes in minibatches of 128 with PPO's clipped objective, \(\epsilon = 0.2\), using plain gradient ascent on the logits. The score is 0 for the uniform policy and 1 for the best possible one. The milestone is 0.9. Each arm runs 40 seeds, and the table reports the median \(D^\star\).

Seeds, early learning and wrong picks

This toy runs the same bandit with one epoch, in two arms that differ only in learning rate: 2.0 for arm A and 2.1 for arm B. Each arm runs 200 seeds.

Measured · a toy problem, not Spire Mentor and not a language model

Arm B reached the 0.9 milestone in 30,927 decisions on average and arm A in 32,220, a difference of 1,293 with a seed-to-seed standard deviation of about 890 in each arm. Picking the arm with the lower mean over resampled seeds, with a tie settled by a coin flip, chose the wrong arm 16% of the time with one seed per arm, 4.0% with three, 1.1% with five and 0.07% with ten. Ties are common at small \(n\) because \(D^\star\) only takes multiples of 512. Equation \eqref{eq:wrongpick}, with \(\Delta^\star/\sigma_\star = 1.45\), gives 15%, 3.8%, 1.1% and 0.06%.

Across seeds, the rank correlation between decisions to 0.5 and decisions to 0.9 was 0.23 for arm A and 0.38 for arm B (Spearman, with tied ranks averaged). Every seed reached 0.5 within the same three iterations of 512 decisions, so the coarse early measurement also weakens the correlation. A seed that started fast was only slightly more likely to finish fast.

This toy's seeds vary far less than deep-RL seeds do. Its spread is about 3% of \(D^\star\), and its distribution is close to normal. Deep-RL seeds can be heavy-tailed or bimodal, which makes small-sample tests fire somewhat more often than their nominal level; Colas et al. measured this, and Henderson et al.'s two significantly different groups drawn from one TRPO configuration are an example.

13. Common confusions

"Sample efficiency is one number." It is at least three: decisions to a milestone, wall-clock time to it, and seeds needed to compare two recipes. The epoch switch in Section 5 raised decisions per second by a measured 43%. It probably raised the decisions needed to reach a milestone, but that is an inference, because \(q\) was never measured. By Equation \eqref{eq:breakeven}, it shortened the wall-clock time to a milestone only if the second epoch's extra gain \(q\) was below 0.41, and the campaign cannot tell whether it was.

"Reusing data always helps, because each decision is expensive." It helps the per-decision count when the reuse is valid, and it costs time per decision. With a fast simulator the decision is the cheap part. Equation \eqref{eq:breakeven} decides, and its two sides have to be measured on the machine and problem at hand.

"A bigger batch is more sample-efficient." Below the critical batch size, with the learning rate re-tuned for each batch, it is about equally efficient per decision and needs fewer updates. Above it, it wastes decisions. A bigger batch at a fixed learning rate also lowers the noise floor, but each halving of the floor buys half the improvement of the last.

"The arm that is ahead after a short run will be ahead at the end." Curves cross, as in Figure 9.1b, and in the bandit toy of Section 12, which is not Spire Mentor, early and late speed were only weakly related even within one recipe. If an early milestone is the endpoint, pre-register it as the endpoint.

14. Suggested experiments

All four run on any machine with Python 3 and NumPy, from the fork's root. None needs the simulator.

Reproduce the figures

  1. Run python3 tour/stop-9-sample-efficiency/figures.py. It prints a summary and redraws every data figure in chapter.html.
  2. Open tour/stop-9-sample-efficiency/figures.json. The campaign section holds each log value with its line number, so you can check any point in Figure 9.3 against docs/experiments/2026-11-03-ironclad-e2e-v111/CAMPAIGN_LOG.md.

Find the learning rate where one epoch wins per second

  1. In figures.py, change the tuple (2.0, 4.0, 8.0) in toy_epochs to (4.0, 5.0, 6.0, 7.0).
  2. Run python3 tour/stop-9-sample-efficiency/figures.py.
  3. Read the last number of each "epochs" entry in the printed summary. It is \(D^\star(1)/D^\star(2)\). The learning rate where it falls below 1.41 is where one epoch would win per second at Spire Mentor's measured time ratio.

Add a fourth doubling to the quadratic

  1. In toy_floor, change b_of to return 8 after 4 * seg steps, and run 5 * seg steps instead of 4 * seg.
  2. Change the line that computes floors to range(5).
  3. Run the script and print the floors with python3 -c "import json; print(json.load(open('tour/stop-9-sample-efficiency/figures.json'))['toy_floor']['schedule']['floors'])". Each new floor should be half the last.

Size a two-arm comparison

  1. In toy_seeds, set arm B's learning rate to 2.05 instead of 2.1.
  2. Run the script and read "wrong_pick" in the printed summary.
  3. Find the smallest seed count with a wrong-pick rate below 5%, and compare it with Equation \eqref{eq:wrongpick} using the printed late_mean and late_sd.
