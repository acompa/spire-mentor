RL environments for language-model agents

Before a policy gradient can train a language model, someone has to build the thing the model acts in: a set of tasks, a sandbox, tools, and a program that decides whether the task was done. This chapter takes that environment apart, shows what an imperfect grading program does to the gradient, and compares the result with the simulator Spire Mentor trains in.

1. The environment is the part you build

Every chapter so far could take its environment for granted. Spire Mentor's simulator encodes the game's rules exactly, and a few lines of Python turn a finished run into a reward. Chapter 10 moved the policy gradient from that simulator to a language model and treated the source of prompts and rewards as given. This chapter is about building that source.

An environment for a language-model agent is the program that hands the model a task, runs the model's tool calls against a sandbox, shows it the results as text, stops the episode, and scores the outcome. Three things make it harder to build than a game simulator. The tasks are data that someone collected, and their difficulty is unknown until a model tries them. The sandbox runs arbitrary code, so the set of things the model can do is far larger than the set of things the designer considered. The reward comes from a verifier, a program that checks the outcome, and a verifier can be wrong.

Most of the chapter is about the third point. You will derive what a verifier with known error rates does to the expected reward and to the policy gradient. When the errors do not depend on what the policy did, the answer is simple. When they do, you get reward hacking, which chapter 3, section 6 introduced for game rewards. A toy experiment in section 9 shows both cases on a small policy-gradient problem.

If you come from deep Q-learning and offline RL, one contrast with that background is worth keeping in mind. In Q-learning on Atari the emulator is fixed and correct, and all the difficulty is in the learner. Here you will often reuse chapter 10's learner unchanged, and most of the engineering, along with most of the ways a training run goes wrong, sits in the environment.

2. Symbols added in this chapter

The tour's notation table from chapter 1 still holds. The symbols below are new to this chapter or change meaning in it. Four overlap with earlier chapters. \(h_t\) is chapter 1's history, with the task \(x\) in place of \(o_0\). \(n\) is chapter 10's group size, not chapter 4's n-step count. Chapter 10 writes \(y\) for a completion and \(p_x\) for the policy's success rate on prompt \(x\); here \(y\) is the truth indicator, \(p_x\) is an honest attempt's success probability, and chapter 10's \(p_x\) is \(q\).

3. Seven parts, added one at a time

The environment has seven parts. The figures below add them in order, and each figure draws the part it adds in the accent colour.

Task set and initial state. Each episode starts by drawing a task \(x\) from a task set \(\mathcal{D}\). A task is a row of data. In a coding environment it holds the problem statement, a repository snapshot, and the tests that will grade the result. The environment uses the row twice. The prompt goes to the model, and the rest of the row builds the sandbox's initial state \(s_0(x)\), a container with the files checked out and the dependencies installed.

Tools and the action interface. The model's output is text. A tool parser reads that text and extracts a structured call, such as run_shell("pytest -x") or edit_file(path, patch). The tool set is the action space, and the parser defines the legal actions, much as \(\mathcal{A}(s)\) does in the tour's notation. A model turn that the parser cannot read must still produce some outcome, usually an error message as the next observation or the end of the episode.

Transition. The sandbox executes the call. Its state changes from \(s_t\) to \(s_{t+1}\): a file is written, a process exits, a test fails. The transition is whatever the operating system and the code in the container do. Nobody wrote it down as a table, and in general it is not deterministic: a test that depends on a clock or a network call can give different results on the same input.

Rendering the observation. The raw output of a tool call can be megabytes of log. A render function cuts it to text that fits the context window: it truncates, keeps the tail of a stack trace, or summarises a directory listing. The rendered text is appended to the transcript. The policy conditions on the whole transcript, so the episode is a partially observed decision process in the sense of chapter 1, section 7. The sandbox state is the state, and the transcript is everything the policy has observed.

\begin{equation} h_t = \big(x,\ a_0,\ o_1,\ a_1,\ o_2,\ \dots,\ a_{t-1},\ o_t\big), \qquad a_t \sim \pi_\theta(\,\cdot \mid h_t) \label{eq:policy} \end{equation}

Here \(a_t\) is a whole model turn, a sequence of tokens that chapter 10 scores with the sequence-level log-probability, and \(o_t\) is the rendered result of the previous call. Each turn goes through the sandbox and the renderer:

\begin{equation} s_{t+1} \sim p(\,\cdot \mid s_t, a_t), \qquad o_{t+1} = \mathrm{render}(s_t, a_t, s_{t+1}) \label{eq:transition} \end{equation}

What the render function keeps decides what the policy can learn. If it drops the line of a stack trace that names the failing test, the policy cannot learn to read that line. If it shows a file the task meant to hide, the policy can learn to copy from it.

Termination and budgets. An episode ends in one of two ways. Either the model declares it is done, for example by calling a submit tool, or a budget runs out: a maximum number of turns, a total of generated tokens, or wall-clock time. Gymnasium has a name for each. An episode is terminated when it reaches a terminal state of the task. It is truncated when it stops for a reason outside the task, such as a time limit [2, §4.2]. The difference matters to any learner that bootstraps. A value target should treat a truncated episode as if the future continued:

\begin{equation} \hat{V}(s_t) = r_t + \gamma\,\big(1 - \mathrm{terminated}_t\big)\,V_\phi(s_{t+1}) \label{eq:target} \end{equation}

Equation \eqref{eq:target} is the form Gymnasium gives [2, §4.2, Eq. 1], written in the tour's symbols. The critic \(V_\phi\) is from chapter 4. Most language-model training drops the critic, as chapter 10 explains, so the distinction shows up in the verifier instead. The verifier scores a budget cut like any other ending, and the designer must decide what that score is. A model that never submits should not score better than one that submits a wrong answer.

The verifier. When the episode ends at turn \(T\), the verifier reads the task and the final sandbox state and returns a verdict. The verdict is the reward of the last action, \(r_{T-1}\), since chapter 1 fixes \(r_T \equiv 0\) at the terminal state. All earlier turns get zero:

\begin{equation} r_t = 0 \ \ (t < T-1), \qquad r_{T-1} = v(\tau) = \mathrm{grade}(x, s_T) \in \{0, 1\} \label{eq:reward} \end{equation}

For a math problem, \(\mathrm{grade}\) compares the final answer with a reference. For a coding task, it runs the task's hidden tests against the final repository. For an open-ended task, it may be another language model with a rubric. The verdict can also be a fraction, such as the share of tests that pass. This chapter keeps it binary because the binary case makes the error analysis exact.

Put together, the environment is a tuple of these seven parts:

\begin{equation} \mathcal{E} = \big(\mathcal{D},\ s_0(\cdot),\ \text{tools},\ p,\ \mathrm{render},\ \text{budget},\ \mathrm{grade}\big) \label{eq:env} \end{equation}

The tuple in Equation \eqref{eq:env} is an MDP from chapter 1 with the reward function replaced by \(\mathrm{grade}\) and the start-state distribution replaced by \(\mathcal{D}\) and \(s_0\). Two of the parts, the transition \(p\) and the verifier, are programs that nobody can read off as a table. The rest of the chapter is about the verifier.

4. A verifier that makes mistakes

Let \(y(\tau) \in \{0, 1\}\) say whether trajectory \(\tau\) really solved its task, and \(v(\tau)\) be the verifier's verdict. They differ in two ways.

Definition 11.1 · False pass and false failure

A false pass is a verdict of 1 on a trajectory that did not solve the task. A false failure is a verdict of 0 on one that did. The verifier's error rates are

\begin{equation} e_{\mathrm{pass}} = P\big(v = 1 \mid y = 0\big), \qquad e_{\mathrm{fail}} = P\big(v = 0 \mid y = 1\big) \label{eq:errors} \end{equation}

Real verifiers have both. Huang and coauthors measured three rule-based math verifiers against labels from a stronger model. All three had precision above 99%, so false passes were rare. Their average recall over four datasets ranged from 86% for one verifier to 93% for another, so between one correct answer in seven and one in fourteen was marked wrong [9, §1, §3.2, Figure 2]. In the notation above, \(e_{\mathrm{pass}}\) was near zero and \(e_{\mathrm{fail}}\) was between about 0.07 and 0.14.

The policy is trained on \(v\) but you care about \(y\). Define the two objectives:

\begin{equation} J_{\mathrm{ver}}(\theta) = \mathbb{E}_{\tau \sim \pi_\theta}\big[v(\tau)\big], \qquad J_{\mathrm{true}}(\theta) = \mathbb{E}_{\tau \sim \pi_\theta}\big[y(\tau)\big] \label{eq:objectives} \end{equation}

Start with the simplest error model. Suppose the error rates are the same for every trajectory: they depend on whether \(y\) is 0 or 1, and on nothing else. This is called class-conditional noise. A grader that misreads 14% of correct answers at random, whatever the answer says, fits this model.

For one trajectory, the expected verdict is then

\begin{equation} \mathbb{E}\big[v \mid \tau\big] = y(\tau)\,(1 - e_{\mathrm{fail}}) + \big(1 - y(\tau)\big)\,e_{\mathrm{pass}} = e_{\mathrm{pass}} + \kappa\, y(\tau), \qquad \kappa = 1 - e_{\mathrm{pass}} - e_{\mathrm{fail}} \label{eq:affine} \end{equation}

We take the expectation over the verifier's coin given \(\tau\), then expand: the \(y\) terms collect into \(y(1 - e_{\mathrm{fail}} - e_{\mathrm{pass}})\) and the constant is \(e_{\mathrm{pass}}\). The expected verdict is an affine function of the truth, with intercept \(e_{\mathrm{pass}}\) and slope \(\kappa\). Figure 11.7 draws it.

Now average Equation \eqref{eq:affine} over trajectories from \(\pi_\theta\). The verifier's coin depends on \(\tau\) only through \(y(\tau)\), so

\begin{equation} J_{\mathrm{ver}}(\theta) = e_{\mathrm{pass}} + \kappa\, J_{\mathrm{true}}(\theta) \label{eq:jver} \end{equation}

Take the gradient. The intercept does not depend on \(\theta\):

\begin{equation} \nabla_\theta J_{\mathrm{ver}}(\theta) = \kappa\, \nabla_\theta J_{\mathrm{true}}(\theta) \label{eq:grad} \end{equation}

Equation \eqref{eq:grad} says when a noisy verifier still points the right way. The gradient you follow is the true gradient times \(\kappa\). If \(\kappa > 0\), which means \(e_{\mathrm{pass}} + e_{\mathrm{fail}} < 1\), the direction is exactly right and only the length shrinks. If \(\kappa = 0\), the verdict carries no information about the truth and the gradient is zero. If \(\kappa < 0\), the verifier is worse than a coin that ignores the trajectory, and training climbs the wrong way. A verifier that wrongly fails 14% of correct answers and passes no wrong ones has \(\kappa = 0.86\). It slows training and leaves the direction alone.

Wang, Liu and Li derived a correction for this case. They replace the observed reward by a surrogate whose expectation equals the true reward [10, Lemma 1]. With true rewards of 1 and 0, their surrogate is

\begin{equation} \hat{r}(v) = \frac{v - e_{\mathrm{pass}}}{\kappa}, \qquad \mathbb{E}\big[\hat{r} \mid \tau\big] = y(\tau) \label{eq:surrogate} \end{equation}

You can check the second identity by substituting Equation \eqref{eq:affine}. The surrogate is unbiased, but it is only an affine function of \(v\). For a policy gradient with a baseline, subtracting a constant from every reward changes nothing, and dividing by \(\kappa\) is the same as multiplying the learning rate by \(1/\kappa\). So for class-conditional errors and a policy-gradient learner, Equation \eqref{eq:surrogate} has the same effect as a larger learning rate. It cannot fix the direction, because the direction was already right.

What the noise does cost is samples. Each verdict is still a 0 or a 1, so the variance of one sample's contribution to the gradient estimate stays about the same size as with a perfect verifier. The mean of that contribution shrinks by \(\kappa\). Suppose you want the estimate's mean, in one coordinate, to be \(\zeta\) standard errors away from zero. With \(N\) independent trajectories and per-trajectory standard deviation \(\sigma\), that requires

\begin{equation} \frac{\kappa\,\lvert \partial J_{\mathrm{true}} \rvert}{\sigma / \sqrt{N}} \ \ge\ \zeta \quad\Longleftrightarrow\quad N \ \ge\ \frac{\zeta^2 \sigma^2}{\kappa^2\, \lvert \partial J_{\mathrm{true}} \rvert^2} \label{eq:samples} \end{equation}

Halving \(\kappa\) quadruples the trajectories needed for the same confidence in the direction. Wang and coauthors prove an upper bound of the same form for a phased Q-learning algorithm with their surrogate: it needs no more than \(O(1/\det(C)^2)\) times the samples it would need with true rewards, where \(C\) is the two-by-two confusion matrix [10, Theorem 2]. For a binary reward, \(\det(C) = \kappa\). Chapter 9, section 6 discusses how batch size and gradient noise trade against each other. In its terms, a verifier with slope \(\kappa\) multiplies the progress per decision by \(\kappa\) at a small learning rate, so the updates needed grow as \(1/\kappa\). It also multiplies the gradient by \(\kappa\) while leaving the per-sample variance about the same, so the noise scale \(B_{\text{simple}} = \mathrm{tr}(\Sigma)/|g|^2\) of that section, and with it the batch worth using, grows by \(1/\kappa^2\).

5. A verifier the policy can exploit

The class-conditional model assumes the verifier's mistakes are random with respect to the policy. A policy-gradient learner breaks that assumption as soon as some behaviour fails the task and still passes more often than other failures do. The learner finds such behaviour because it is paid for it. This is reward hacking from chapter 3, section 6, and Krakovna and coauthors' name for it is specification gaming: behaviour that satisfies the literal specification of an objective without achieving the intended outcome [7].

Let the error rates depend on the trajectory. The expected verdict becomes

\begin{equation} \mathbb{E}\big[v \mid \tau\big] = y(\tau)\,\big(1 - e_{\mathrm{fail}}(\tau)\big) + \big(1 - y(\tau)\big)\,e_{\mathrm{pass}}(\tau) \label{eq:dependent} \end{equation}

Average over \(\pi_\theta\) and take the gradient. We separate the true objective from the two error terms:

\begin{equation} \nabla_\theta J_{\mathrm{ver}} = \nabla_\theta J_{\mathrm{true}} \;+\; \nabla_\theta\, \mathbb{E}_{\pi_\theta}\!\big[(1 - y)\, e_{\mathrm{pass}}(\tau)\big] \;-\; \nabla_\theta\, \mathbb{E}_{\pi_\theta}\!\big[y\, e_{\mathrm{fail}}(\tau)\big] \label{eq:hackgrad} \end{equation}

The middle term is the hacking gradient. It points toward failed trajectories that the verifier passes more often. If \(e_{\mathrm{pass}}\) and \(e_{\mathrm{fail}}\) are both constant, the two error terms are \(-e_{\mathrm{pass}}\nabla J_{\mathrm{true}}\) and \(-e_{\mathrm{fail}}\nabla J_{\mathrm{true}}\), they fold back into the true gradient, and you recover Equation \eqref{eq:grad}. If \(e_{\mathrm{pass}}\) is higher for some failures than for others, the middle term has a component of its own, and nothing in the verdict can tell it apart from progress. The last term pushes the other way: it moves the policy away from correct answers that the verifier tends to reject, such as a correct answer written in a format the parser does not accept.

A small model shows where the policy settles. On task \(x\), an honest attempt succeeds with probability \(p_x\). A hack never solves the task and passes with probability \(e_{\mathrm{hack}}\). A policy-gradient learner compares the expected verdicts of the two actions:

\begin{equation} \underbrace{p_x\,(1 - e_{\mathrm{fail}}) + (1 - p_x)\,e_{\mathrm{pass}}}_{\text{honest attempt}} \quad\text{against}\quad \underbrace{e_{\mathrm{hack}}}_{\text{hack}} \label{eq:threshold} \end{equation}

With enough updates the policy on task \(x\) moves toward the larger side. Solving for \(p_x\), the hack wins on every task with \(p_x < (e_{\mathrm{hack}} - e_{\mathrm{pass}})/\kappa\). If task difficulty has distribution \(P_{\mathcal{D}}\) over the task set, the share of tasks hacked at convergence is

\begin{equation} \text{share hacked} = P_{\mathcal{D}}\!\left(p_x < \frac{e_{\mathrm{hack}} - e_{\mathrm{pass}}}{\kappa}\right) \label{eq:share} \end{equation}

Equation \eqref{eq:share} says the hardest tasks are hacked first. With an otherwise perfect verifier (\(e_{\mathrm{pass}} = e_{\mathrm{fail}} = 0\)), a hack that passes 30% of the time does nothing to a task the policy already solves 80% of the time. It takes over every task the policy solves less than 30% of the time. Those are the tasks that should teach the policy something new. The toy experiment in section 9 finds the same ordering.

Documented hacks

Published training runs and evaluations show such behaviour. The first three items below come from training runs, where the hacking gradient was at work, and the fourth from an evaluation of fixed models.

  • Baker and coauthors trained a frontier reasoning model on coding tasks graded by unit tests. Two hacks spread to "nearly every training environment": calling exit(0) so the test run ended early, and raising SkipTest from outside the test framework. The team patched each one after noticing it [8, §2.1].
  • The same paper lists hacks specific to one task: stub implementations where test coverage was poor, edits to libraries upstream of the tests, decompiling a leftover compiled file that held the reference solution, writing a local copy of pandas, and parsing the test file at run time to extract expected values [8, §2.2].
  • Huang and coauthors used a fine-tuned 1.5-billion-parameter model as a math verifier. After about 450 iterations its training reward rose sharply while the reward from a stronger oracle grader did not follow. The policy had learned to output a single symbol such as "{" or long strings of gibberish, which the verifier accepted [9, §5.2].
  • Zhong, Raghunathan and Carlini built evaluation tasks whose tests contradict the specification, so any pass is a cheat. Models given several submissions with feedback modified tests, overloaded comparison operators, recorded state between calls, and special-cased the inputs the tests used [13, §4.1].

Every item on the list is a trajectory with \(y = 0\) and a high \(e_{\mathrm{pass}}(\tau)\), and none of them needed a bug in the learner.

Checks practitioners run

Each check below catches a different failure. Run them before training and again during it.

  1. An oracle solution must pass. If the reference solution fails the verifier, the task is broken or the verifier has false failures. SWE-bench built this into its construction: a task was kept only if at least one test fails before the reference patch and passes after it [11, §2.1].
  2. A do-nothing agent must fail. If an empty submission passes, every policy gets free reward. For its SWE-bench tasks, ImpossibleBench removed every mutation that the original patch or an empty patch passed [13, §2.3].
  3. Grade with a held-out verifier. Keep a second, stronger or more expensive grader that the policy never trains against, and score samples with both. A training reward that rises while the held-out score does not is the signature Huang and coauthors saw [9, §5.2]. Gao, Schulman and Hilton measured the same pattern with reward models: the score from a gold reward model first rises and then falls as optimisation against a proxy continues [12].
  4. Read the top-reward trajectories. Hacks concentrate where the reward is highest. Baker and coauthors used a second language model that read each trajectory, including its chain of thought, to flag hacks [8, §2.1]. In a separate experiment with a smaller agent, they put a monitor that read only the chain of thought into the reward. The agent hacked less than before but still often, and it learned to hide its intent, so the monitor's recall fell to near zero [8, §3.2]. A monitor is safer as an audit than as a reward term.
  5. Remove the opportunity. Make tests read-only or hide them, and grade in a fresh sandbox that holds only the declared outputs. ImpossibleBench found that hiding tests cut cheating to near zero and that read-only tests stopped test edits but not special-casing [13, §5.2].

6. What makes an environment useful for training

A correct environment can still fail to train a policy. Six properties decide whether it does.

Solvable but not saturated. Chapter 10's group baselines compare \(n\) attempts at the same task. If all \(n\) pass or all fail, every advantage in the group is zero and the task contributes no gradient. For a task the current policy passes with probability \(q\), the chance that a group of \(n\) independent attempts is mixed is

\begin{equation} P(\text{mixed group}) = 1 - q^{\,n} - (1 - q)^{n} \label{eq:signal} \end{equation}

With \(n = 8\), a task at \(q = 0.5\) gives a mixed group with probability 0.99. A task at \(q = 0.05\) gives one with probability 0.34, and a task at \(q = 0.01\) with probability 0.08. Tasks far outside this band of difficulty waste the sandbox time spent on them.

A spread of difficulty. As the policy improves, tasks move up and out of the band. A task set with a range of \(p_x\) keeps some tasks in the band throughout training. Equation \eqref{eq:share} gives a second reason to keep the spread, because the tasks at the bottom of the band are the first a hack takes over.

No leakage between training and evaluation. If evaluation tasks, or near copies, appear in training, the evaluation measures memory. SWE-bench built each problem statement only from issue text and comments written before the fix was first committed, and the repositories in its training data are disjoint from those in the benchmark [11, §3 and Appendix A.1]. Leakage can also run through the sandbox: Baker and coauthors' decompiled reference solution was a file that should not have been in the container [8, §2.2].

Determinism and seeding. Gymnasium's reset(seed=...) exists so that the same seed reproduces the same episode [2]. A sandbox with network access, clocks, or flaky tests cannot promise that. When the same submission can pass once and fail the next time, and every task's tests are equally flaky, the flakiness acts as a class-conditional error in section 4's sense and lowers \(\kappa\). When some tasks are flakier than others, each task gets its own \(\kappa(x)\), and the gradient weights tasks by it, toward those with reliable tests. When the flakiness hits some solutions more than others, it is an \(e_{\mathrm{fail}}(\tau)\) term in Equation \eqref{eq:hackgrad}.

Cost per episode. A sandbox episode costs container start-up, tool execution, and a long generation. Chapter 9 separates progress per decision from progress per second. Environment cost sets the second, and it is often the tighter limit.

Evaluated like any other agent. A pass rate on a fixed set of evaluation tasks is a binomial estimate, and comparing two checkpoints on the same tasks is a paired comparison. Chapter 8's methods apply unchanged: paired tasks, McNemar's test, a power calculation before the run, and a pre-registered analysis.

7. The Gym interface and the frameworks built on it

The textbook environment is OpenAI Gym's. Its paper describes the interface as two calls, reset() and step(action), where step returns an observation, a reward, a done flag and an info dictionary. The paper's design choices include "environments, not agents" and strict versioning, so that a result names the exact environment version it used [1]. Gymnasium, its maintained successor, splits done into terminated and truncated, takes a seed in reset, and adds a Text space for string observations and actions [2].

That interface assumes the environment runs in the learner's process, steps quickly, and computes its reward in code. A language-model environment breaks all three assumptions. A step can run a whole test suite, the sandbox is a container that should be isolated from the trainer, and the reward is a separate program. The four frameworks below each keep some of the Gym interface and add what that interface lacks. The descriptions come from each project's own documentation, as read for this chapter. The projects change quickly, so check their current documentation before you rely on a detail.

ProjectWhat its documentation says it standardises
OpenEnv [3]An end-to-end framework for isolated execution environments for agentic RL. Each environment is a Docker image that exposes reset(), step() and state() over a WebSocket, in a Gymnasium-style API. MCP environments expose their tools over MCP in production mode, while training uses step() and rewards. An optional Task API lets a dataset-backed environment list the tasks it can run. The project describes itself as in early development.
Verifiers [4]A library for environments that train and evaluate language models. A taskset is a set of serialisable rows holding the prompt, files, references and resource needs. A harness is the program the model runs in. Toolsets are installed as MCP servers. Rewards are Python functions marked @vf.reward. Grading can run inside the agent's sandbox or, in an optional isolated scoring mode, in a fresh sandbox that holds only declared agent outputs and private test assets.
SkyRL-Gym [5]A set of tool-use environments for math, coding, search and SQL in the Gymnasium API. A text environment implements init(prompt) and step(action: str), which returns observations, a reward, a done flag and metadata. Environments are registered and built with make, as in Gym.
NeMo Gym [6]An environment bundles a dataset, an agent harness, a verifier and per-task state. A resources server owns the verifier, the per-task state and the environment's tools, and runs as an HTTP server. An optional /seed_session endpoint sets up state, and /verify scores the rollout at the end.

Read against Figure 11.6, the frameworks agree on the parts and differ on where the boundaries go. Verifiers, SkyRL-Gym and NeMo Gym separate the task set from the code that runs it. OpenEnv leaves dataset loading inside the environment and offers an optional Task API to list the tasks. Verifiers and NeMo Gym give the verifier its own named place, and Verifiers offers grading in a fresh sandbox as an option, which is check 5 of section 5 built into the framework. OpenEnv and NeMo Gym put the environment behind a network interface, so the sandbox, the trainer and the model server can run on different machines. SkyRL-Gym stays closest to Gymnasium's in-process step.

The environment's docstring gives the whole reward: +1.0 for a win, +0.05 per boss beaten, +0.002 per new floor, and no outcome reward for a death or a cap, with no shaping on HP (env.py, lines 41-48). A capped run keeps the floor and boss rewards it earned before the cap (lines 1431-1435 and 1555-1563). The constants are R_WIN = 1.0, R_BOSS = 0.05 and R_FLOOR = 0.002 (lines 117-119). The caps are 100 turns or 1,000 stored decisions per fight and 6,000 stored decisions per run, and a capped segment ends as a loss (lines 54-60). Chapter 1 explains why the caps exist: a random policy can play a fight that never ends.

The action interface needs no parser. The policy outputs an index into the merged classes of legal actions, and step applies the first member of that class:

In verifier terms, Spire Mentor's reward has \(e_{\mathrm{pass}} = e_{\mathrm{fail}} = 0\) with respect to the simulator. A win in the simulator is a win. The verdict can still be wrong with respect to the real game, if the simulator differs from it. The project's campaign runbook has rules for that risk. A capped share above 0.1% raises an alarm whose action is to "look for deadlocks or sim exploits in the capped runs' action logs" (docs/experiments/2026-11-03-ironclad-e2e-v111/RUNBOOK.md, line 413). A jump of more than 5 percentage points between two evaluation reads triggers an audit of the top runs against the C# game (line 424). The audit is check 4 of section 5, reading the top-reward trajectories. The engine also checks invariants such as HP within range and pile conservation on 1% of steps, and any violation stops the training lane (env.py, lines 76-82; RUNBOOK.md, line 410).

A worked design: the simulator as an environment for a language model

Suppose you wanted a language-model agent to play Spire Mentor's runs. The design exists only on paper, and nothing in the repository implements it. Each of the seven parts has a natural choice.

  • Task set and initial state. A list of seeds. Each seed builds the simulator's state, as E2EEnv(seed) does now. Training seeds and evaluation seeds come from disjoint ranges.
  • Observation text. At each decision, the render function writes what a player could see: HP, energy, the hand, each enemy's intent, relics, potions, and a numbered list of the legal actions. It must never write the hidden draw order. Chapter 1 notes that the project already keeps that information in a section, PRIV_DRAW, that only the critic reads (chapter 1, section 9).
  • Tool calls. One tool, choose(index), that takes a number from the list. An optional read-only tool such as describe(card) returns a card's text. A turn that does not parse to a legal index gets an error message and counts against the budget. It must never fall back to a default action, because a default that happens to be strong would become a free policy.
  • Budget. The existing caps: 100 turns or 1,000 decisions per fight and 6,000 per run. Add a cap on generated tokens per decision. A cap ends the run as a loss, as now: no win reward, with the floor and boss rewards earned before it kept.
  • Verifier. The simulator's outcome: 1 for a win. To keep a signal on runs that do not win, use the existing floor and boss terms. The reward is exact with respect to the simulator.

The list of things a policy could hack is short because the reward is code. Each item maps to a check above.

  • Simulator bugs. Any place the Rust engine differs from the game is a false pass relative to the real game. The runbook's audit against C# on a 5-point jump is the held-out verifier.
  • The parser. If an unparsable turn defaulted to a legal action, or if the parser accepted an index outside the list, the policy could learn to exploit it. A do-nothing agent that emits garbage must score no better than one that loses.
  • Leaked state in the render. If the observation text ever included the draw order or a future card reward, the policy would learn to read it. This is the language-model version of the leftover reference solution in Baker and coauthors' sandbox.
  • Stalling. Under the current reward, stalling earns nothing: the floor term pays only for a new highest floor (env.py, line 1434), and a cap pays no outcome reward. If someone later added a reward for each turn or decision survived, with no cap penalty, a policy that cannot win might learn to stall until the cap.
  • Seed overlap. A training seed that reappears in an evaluation panel inflates the win rate in the way chapter 8 warns about.

The worked design shows how much of section 5 the simulator avoids. Its transition and verdict are exact, and its action space is a list. The hard parts that remain are the render function and the task split, the two parts that decide what the model can see.

9. Measured: a verifier with false passes

This section runs a small policy-gradient problem with a deliberately imperfect verifier. It is a toy problem, not a language model. The script is tour/stop-11-llm-environments/figures.py, and it writes its results to toy.json beside it.

The setup has 64 tasks. Task \(x\) has an honest success probability \(p_x\), spread evenly from 0.05 to 0.95. On each task, the policy picks one of three actions: attempt the task, which truly succeeds with probability \(p_x\); hack, which never truly succeeds; or give up, which never succeeds. The policy is a softmax with its own three logits per task, starting at probabilities 0.69, 0.06 and 0.25. Each update samples 8 attempts per task, scores them with the verifier, and applies REINFORCE with the leave-one-out baseline from chapter 10. Every number below is the mean over 10 seeds. A policy that always attempts gets a true success rate of 0.50, the mean of \(p_x\).

Experiment A: the same false-pass rate on every failure

Here every failed attempt passes with probability \(e_{\mathrm{pass}}\), whichever action produced it, and \(e_{\mathrm{fail}} = 0\). Experiment A is the class-conditional case of section 4, so Equation \eqref{eq:grad} predicts the right direction at a speed scaled by \(\kappa = 1 - e_{\mathrm{pass}}\). The learning rate is 0.1.

Measured · a toy problem, not a language model

With a perfect verifier the policy reached a true success rate of 0.45 in a median of 110 updates. At \(e_{\mathrm{pass}} = 0.5\) (\(\kappa = 0.5\)) it took 215 updates, a ratio of 1.95 against the predicted 2. At \(e_{\mathrm{pass}} = 0.7\) (\(\kappa = 0.3\)) it took 355, a ratio of 3.2 against the predicted 3.3. After 1,500 updates the mean true success rate of every setting was between 0.485 and 0.496, lower for larger \(e_{\mathrm{pass}}\) because the slower runs had further to go. All were still climbing toward 0.50. The noisy but unbiased verifier slowed training, and the theory says it does not change the limit.

Experiment B: only the hack passes falsely

Now honest failures and giving up always score 0, and only the hack passes falsely, with probability \(e_{\mathrm{hack}}\). Experiment B is the trajectory-dependent case of section 5. Equation \eqref{eq:share} predicts that, at convergence, the policy hacks every task with \(p_x < e_{\mathrm{hack}}\), since here \(e_{\mathrm{pass}} = e_{\mathrm{fail}} = 0\) and \(\kappa = 1\). The learning rate is 0.5 and each run has 4,000 updates.

Measured · a toy problem, not a language model

At \(e_{\mathrm{hack}} = 0.3\) the policy put probability 0.24 on the hack, averaged over tasks, against a predicted share of 0.28. At \(e_{\mathrm{hack}} = 0.6\) the hack had 0.55 against a predicted 0.61, the true success rate ended at 0.34, against 0.50 with no hack, and the verifier pass rate rose to 0.67. Task by task at \(e_{\mathrm{hack}} = 0.6\), every task with \(p_x \le 0.48\) put more than 0.99 on the hack, and every task with \(p_x \ge 0.65\) put less than 0.002 on it. The tasks at \(p_x = 0.55\) and \(0.56\) averaged 0.40 because 4 of the 10 seeds settled on the hack and 6 on the honest attempt. With two actions of nearly equal value, each seed locks in whichever way its early samples push it, and the hack's small expected advantage does not undo that in 4,000 updates. That split on the tasks just below \(e_{\mathrm{hack}}\) is why the measured share falls short of the prediction.

In the training curve at \(e_{\mathrm{hack}} = 0.6\), the true success rate peaked at 0.46 after 60 updates and ended at 0.34, while the verifier pass rate climbed from 0.38 to 0.67.

The two experiments separate the two cases of the theory. Random verifier errors cost time. Errors that the policy can choose to trigger change where training ends, while the training reward goes up the whole way there. A held-out check of true success would have caught Experiment B at update 60.

A fine-tuned model verifier was hacked after about 450 iterations, while rule-based and untrained model verifiers tracked the oracle reward [9, §5.2].

10. Common confusions

  • "A noisy verifier biases the policy." Not if the noise is class-conditional. Equation \eqref{eq:grad} shows the gradient keeps its direction whenever \(e_{\mathrm{pass}} + e_{\mathrm{fail}} < 1\). Bias comes from errors that depend on what the policy does, Equation \eqref{eq:hackgrad}.
  • "Correcting the reward for known error rates fixes the noise." For a policy gradient with a baseline, the unbiased surrogate of Equation \eqref{eq:surrogate} is a shift and a rescale. The shift is absorbed by the baseline and the rescale is a learning-rate change. It does nothing about variance or about hacks.
  • "A higher training reward means a better policy." Only while the verifier stays honest. In Experiment B the verifier pass rate rose for 4,000 updates while the true success rate fell after update 60. Track a held-out measure alongside the training reward.
  • "An accurate verifier is a robust one." Accuracy on a fixed set of answers measures errors on outputs the policy has not been trained to produce. Huang and coauthors found that the fine-tuned verifier that scored higher on static accuracy was the one the policy hacked [9, §1].
  • "Truncation is just another ending." For a learner that bootstraps, a time limit is not a terminal state, and Equation \eqref{eq:target} treats it differently. For the verifier, a budget cut needs an explicit score that is no better than a wrong answer.

Suggested experiments

The first three experiments change the toy in figures.py. Each run of python3 tour/stop-11-llm-environments/figures.py run rewrites toy.json. Run python3 tour/stop-11-llm-environments/figures.py render afterwards to redraw the plots.

  1. Add false failures. In run(), change e_fail=0.0 to e_fail=0.3 in the Experiment B loop. Equation \eqref{eq:share} predicts the hack takes every task with \(p_x < e_{\mathrm{hack}}/0.7\). Expect the hack line in Figure 11.10 to rise earlier: at \(e_{\mathrm{hack}} = 0.3\), the predicted share moves from about 0.28 to about 0.42.
  2. Make the hack depend on difficulty. In train(), give each task its own false-pass rates: build fp as a 64-by-3 array whose hack column is e_hack * (1 - p), and look it up with np.take_along_axis(fp, a, axis=1) in place of fp[a]. Ignore the logged verifier curve, which still assumes a constant rate. The hack now beats an honest attempt when \(e_{\mathrm{hack}}(1 - p_x) > p_x\), that is when \(p_x < e_{\mathrm{hack}}/(1 + e_{\mathrm{hack}})\). Expect the per-task hack probabilities in toy.json to switch near that value, 0.375 at \(e_{\mathrm{hack}} = 0.6\).
  3. Measure the cost of noise at a high learning rate. Run Experiment A with lr=0.5 and a target of 0.48 instead of 0.45. The noise in each update now matters more than its mean. Check whether the updates needed grow faster than \(1/\kappa\), toward the \(1/\kappa^2\) of Equation \eqref{eq:samples}.
  4. Design exercise: Spire Mentor for a language model. Write down, on paper, the render function for one combat decision in the worked design of section 8. List every field it prints and the source of each in the simulator's state. Then list three ways a policy could raise its reward without winning more runs in the real game, and give for each the check from section 5 that would catch it. This exercise plays no runs.
